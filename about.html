О проекте — DevSecOps Scanner

Сканер уязвимостей REST API + учебный стенд
Документ № DOC-001
Редакция 2.1
Название DevSecOps Scanner
Назначение Автоматизированный аудит безопасности REST API с отчётами и историей
Целевой стек FastAPI, Python 3.10+
Режим запуска Одна команда python start.py — поднимает два сервера
01 Что это

DevSecOps Scanner — учебно-прикладной инструмент для проверки REST API на типовые уязвимости. Состоит из двух частей:

  • Сканер (web_app.py, порт 8001) — веб-интерфейс, который запускает проверки, ведёт живой лог, строит графики и формирует отчёты в 5 форматах.
  • Уязвимый стенд (main.py, порт 8000) — намеренно уязвимый FastAPI-сервис, на котором можно безопасно тренировать сканер и проверять его работу.

Стенд рандомизирует набор уязвимостей при каждом старте сканирования: SQLi, IDOR, BFLA и заголовки безопасности включаются/выключаются с вероятностью ~80%. Поэтому каждый новый скан даёт другой набор находок, а график истории — живой.

Зачем это нужно. Сканер учится находить те же классы уязвимостей, что и коммерческие DAST-инструменты (OWASP ZAP, Burp), но на контролируемом стенде и без юридических рисков для чужих API.
02 Быстрый старт

Windows — установка один раз:

# Создание виртуального окружения
python -m venv venv

# Активация (PowerShell)
Set-ExecutionPolicy -ExecutionPolicy Bypass -Scope Process -Force
.\venv\Scripts\Activate.ps1

# Установка зависимостей
pip install -r requirements.txt

Запуск (без активации venv, чтобы не зависеть от политики PowerShell):

.\venv\Scripts\python.exe start.py

Linux / macOS:

python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
chmod +x run.sh
./run.sh

Лаунчер start.py автоматически:

  • переходит в папку скрипта — запускать можно из любой директории;
  • проверит и поставит все зависимости в venv;
  • скачает Chromium для Playwright внутрь venv (venv/.playwright-browsers) — в систему ничего не летит;
  • найдёт свободные порты, если 8000 / 8001 заняты;
  • откроет браузер на http://127.0.0.1:8001;
  • корректно остановит оба сервера по Ctrl + C.

Логин в UI: admin / admin (полный доступ).
Гостевой режим: guest / guest (только просмотр).

03 Возможности сканера
Режимы сканирования
Быстрый — только ключевые проверки.
Полный — все 24 проверки.
Свои — галочками выбираются конкретные проверки.
Авторизованные сканы
Два аккаунта (user1 / user2). Сканер логинится сам, получает токены и проверяет cross-user IDOR и BFLA.
Живой прогресс
WebSocket-лог в реальном времени, прогресс-бар, счётчики по уровням, Security Score (0–100).
Отчёты
HTML, JSON, CSV, XLSX и PDF (серверный рендер через headless Chromium). Плюс ZIP-архив со всеми форматами сразу.
История и аналитика
Все сканы в SQLite. График динамики уязвимостей, экспорт всей истории в XLSX, удаление отдельных записей.
Роли UI
admin — полный доступ.
guest — только просмотр (сканирование, история и отчёты недоступны).

Security Score считается по формуле 100 − (CRITICAL×20 + HIGH×10 + MEDIUM×5 + LOW×2), минимум 0:

  • 80+ — зелёный (защита в порядке);
  • 50–79 — жёлтый (требует внимания);
  • 20–49 — фиолетовый (много проблем);
  • < 20 — красный (критическая ситуация).
04 Уязвимый стенд

Сервис main.py реализует следующие уязвимости. Каждая включается случайно при новом скане (см. профиль скана).

Уязвимость Эндпоинт / проявление Уровень
SQL Injection /api/users/{id} — конкатенация ввода в SQL-запрос CRITICAL
IDOR / BOLA /api/orders/{id} — доступ к чужому заказу без проверки владельца CRITICAL
BFLA /api/admin/users — обычный user получает админский список CRITICAL
Sensitive Data Leak /api/system/keys — AWS-ключ и пароль БД в открытом виде HIGH
Business Logic Отрицательные ID в /api/users/{id} обрабатываются как валидные HIGH
Error Leak Утечка sqlite3-ошибок в ответе MEDIUM
Missing Headers Случайное отсутствие X-Frame-Options, CSP, HSTS и др. MEDIUM
Рандомизация. Профиль уязвимостей генерируется на каждый скан отдельно — по запросу /openapi.json с заголовком X-Scan-Start: 1. Поэтому в одном скане активна SQLi, а IDOR отключён, в следующем — наоборот. График истории всегда показывает разные точки.
05 Проверки сканера

Всего реализовано 24 проверки, сгруппированные по категориям.

Категория Что проверяется
Инъекции SQL Injection (error-based, boolean-based, time-based: SLEEP / pg_sleep / WAITFOR); OS Command Injection (;id, |id, $(id), `id`); Reflected XSS (5 payload'ов для HTML и атрибутов)
Контроль доступа IDOR (общая эвристика «разные ID → разные данные»); IDOR auth vs аноним (сравнение ответов с токеном и без); Cross-user IDOR / BOLA (user1 читает данные user2); BFLA (обычный user получает админский эндпоинт); CSRF (эвристика по токену / cookie, кроме login-роутов); CORS (Access-Control-Allow-Origin: *); CAPTCHA (10 попыток логина без блокировки)
Заголовки и TLS Security Headers (X-Frame-Options, X-Content-Type-Options, X-XSS-Protection); CSP (Content-Security-Policy); HSTS (Strict-Transport-Security); TLS (отсутствие HSTS на HTTPS); Unsafe HTTP methods (PUT / DELETE / TRACE)
Данные Sensitive Data Exposure (AWS-ключи, пароли, API-ключи, приватные ключи); SCA (поиск /package.json, /requirements.txt, /pom.xml)
Логика Business Logic Error (отрицательные ID); Pagination (сервер отдаёт всё без лимита); Mass Assignment (лишние поля is_admin, role); GraphQL Introspection (открыт __schema)
Прочее Hidden Paths (/admin, /backup, /.env, /metrics); HTTP без HTTPS; Content-Type Validation (принимает text/plain); Rate Limiting (50 запросов без блокировки); Error Leak (stack-trace в ответе)
06 Отчёты

Сканер формирует отчёты в пяти форматах плюс ZIP-архив со всем сразу.

Формат Назначение
HTML / PDF Официальный документ со сводкой, диаграммой и таблицей находок. PDF рендерится на сервере через headless Chromium — без системных колонтитулов браузера.
JSON Для интеграции с CI/CD и внешними системами.
CSV Разделитель ;, UTF-8 BOM — корректно открывается в Excel.
XLSX Excel-файл с настройкой ширины колонок, цветами уровней, автофильтром и заморозкой шапки. Работает в Excel, LibreOffice, ONLYOFFICE, Google Sheets.
ZIP Один архив со всеми форматами сразу. Chart.js инлайнится в HTML, поэтому отчёт открывается офлайн — без сервера.

Экспорт всей истории. Кнопка «ЭКСПОРТ ИСТОРИИ (XLSX)» на вкладке «История» формирует сводную таблицу по всем сканам: ID, дата, цель, оценка, счётчики по уровням.

Три независимых компонента работают вместе:

Пользователь

Сканер

⇄
SQLite

Уязвимый стенд

Сканер шлёт запросы на стенд, собирает находки,
сохраняет в SQLite, отдаёт в UI и в отчёты.

Поток данных одного скана:

  1. Пользователь жмёт «Запустить» в UI.
  2. Сканер POST-ит на /scan, создаётся задача.
  3. Открывается WebSocket на /ws/scan/{task_id}.
  4. В фоновом потоке сканер логинится в стенд, дёргает /openapi.json с X-Scan-Start: 1 (стенд генерирует новый профиль уязвимостей).
  5. 24 проверки прогоняются последовательно, находки летят в UI по WebSocket.
  6. Результат сохраняется в SQLite (scans.db) — до того, как UI получит статус «ГОТОВО».
  7. Пользователь может скачать отчёты и посмотреть график динамики.

10 Что вводить при сканировании

Минимальная проверка «всё ли работает» — 30 секунд:

Поле Значение
Целевой URLhttp://127.0.0.1:8000
РежимПолный
Аккаунт 1alice / alice123
Аккаунт 2bob / bob123
  1. Открой http://127.0.0.1:8001, войди как admin.
  2. Заполни поля из таблицы выше.
  3. Нажми ЗАПУСТИТЬ.
  4. В логе должны появиться строки: 
    [ИНФО] Аккаунт 1: OK, токен получен
[ИНФО] Аккаунт 2: OK, токен получен
  5. В отчёте — от 5 до 20 находок, из которых обычно 1–4 CRITICAL.
Зачем два аккаунта. Сканер сам логинится под каждым, получает токены и проверяет, может ли alice прочитать заказы bob'а. Это Cross-user IDOR — уязвимость №1 в OWASP API Top 10.

Если аккаунты не заполнены, скан всё равно запустится, но проверит только то, что видно анонимно. Cross-user IDOR, BFLA и защищённые эндпоинты будут пропущены.
